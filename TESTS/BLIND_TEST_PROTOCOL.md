# V10 Blind Test Protocol v0.3

## 目的
把两个问题分开测试，避免把“能力恢复”和“私有 GitHub 访问”混成一个成绩：

A. 一个完全不使用旧 Memory 的新会话，仅凭 V10 文件能否恢复 95%+ 创作能力。
B. 一个能访问私有 GitHub 的新会话，能否稳定执行仓库启动流程。

---

## Test A：严格能力恢复测试（最高优先级）

### 环境
1. 新建 Temporary Chat / 临时聊天。
2. 开始前选择 Unpersonalized / 不使用个性化。
3. 不使用 Memory、Custom Instructions、Plugins 或旧聊天背景。
4. 将本仓库当前测试版本的 ZIP/文件直接提供给被测会话；或者使用无需插件即可访问的公开测试镜像。
5. 除测试启动指令外，不补充任何 V10 项目背景。

### 被测会话流程
1. 读取 `V10_SKILL.md`。
2. 严格执行其中恢复流程。
3. 读取 `TESTS/BLIND_TESTS.md`。
4. 一次性回答全部 40 题。
5. 不向用户索取背景。
6. 材料不足时明确标记“依据不足”，不得凭空补写。
7. 回答后给出不超过 200 字自检。

### 通过标准
- 38/40 = 95%，通过。
- 40/40 = 当前最优。
- 任何核心硬设定出现致命错误，即使总分达到 38，也必须复查 Runtime。

Test A 才是“V10 文件本身能否把失忆模型重新编译成作者”的主验收。

---

## Test B：私有 GitHub 启动链路测试

### 环境
1. 使用可访问 GitHub 连接器的新聊天。
2. 尽可能关闭/隔离 Memory 后再开始测试。
3. 测试消息只提供私有仓库地址与启动任务，不补充 V10 背景。

### 被测会话流程
1. 从私有仓库读取 `V10_SKILL.md`。
2. 按 Skill 规定读取 Runtime、Canon、Current、Index。
3. 报告实际读取到的文件与版本。
4. 完成若干抽样测试题或全部 40 题。

### Test B 验收重点
- 能否访问仓库。
- 是否会自动找到唯一入口。
- 是否按固定顺序读取。
- 是否漏文件。
- 是否在无法确认时回查 Canon。
- 是否要求用户重复仓库里已有信息。

Test B 不单独证明“无 Memory 恢复能力”，它只证明私有 GitHub 工作链路可用。

---

## 结果记录

每轮测试必须记录：
- Runtime 版本
- 测试类型（A 或 B）
- 测试环境
- 总分
- 错题编号
- 错误类型：硬设定 / 创作原则 / 连续性 / 原创应用 / 启动流程
- 是否可能受到旧 Memory 污染

只有 Test A 达到 38/40 以上，才能正式宣称“V10 Runtime 文件恢复率达到 95%+”。
